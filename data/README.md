# `data/` — synthetic chest-radiograph generator

A procedural pipeline that turns a sampled clinical scenario (e.g. *congestive heart failure*, *miliary tuberculosis*, *normal*) into:

- a 320 × 320 grayscale PNG with realistic background anatomy (ribs, vasculature, mediastinum, diaphragm) plus the rendered findings on top;
- a per-finding **soft segmentation mask** with Gaussian-edged falloff (`<dataset>/masks/<id>.npz`, uint8 NPZ keyed by finding label);
- a **free-text radiology report** with sectioned (`TECHNIQUE / CLINICAL INDICATION / COMPARISON / FINDINGS / IMPRESSION`) and prose styles, randomized per sample;
- multi-label CSV with three label tiers — atomic findings, computed counts/sizes/bilateralities, and clinical syndromes — derived deterministically from the same `FindingState`.

## Clinical taxonomy

Three label tiers — see [`findings.py`](findings.py) for the full schema.

| tier | example labels | source |
|---|---|---|
| **atomic** (15)   | `cardiomegaly`, `effusion_left/right`, `pneumothorax_left/right`, `pleural_thickening_*`, `volume_loss`, `consolidation`, `consolidation_air_bronchogram`, `reticular_pattern`, `honeycombing`, `kerley_b_lines`, `pulm_venous_redistribution`, `hilar_adenopathy` | what the renderer paints |
| **computed** (~15) | nodule counts, size variability, bilateralities, micronodule density bins | derived from atomic state |
| **syndromes** (10) | `chf_syndrome`, `uip_pattern`, `sarcoidosis_pattern`, `tb_pattern`, `mesothelioma_pattern`, `tension_pneumothorax`, `metastatic_pattern`, `miliary_pattern`, `solitary_pulmonary_nodule`, `lobar_pneumonia_pattern` | constellations of atomic findings, encoding published radiology criteria |

The criteria for each syndrome are defined in `derive_labels()` and exported as text in `finding_definitions.json` next to each generated dataset.

## Soft segmentation masks

Each rendered finding is captured by snapshotting the canvas before and after its draw call; the absolute delta is the per-finding contribution. Multiple instances of the same type (e.g. several nodules) are merged via max-blend into one combined mask per type and normalized to `[0, 1]`. Stored as a single NPZ per image:

```
masks/img_00001.npz
    cardiomegaly        : (320, 320) uint8 in [0, 255]
    effusion_left       : ...
    consolidation       : ...
    nodules             : ...
```

Loading: `mask = np.load(path)["cardiomegaly"].astype(np.float32) / 255.0`. The NPZ is compressed; typical per-image size is ~10 kB.

## Reports

[`reports.py`](reports.py) generates radiology reports designed to imitate the language of real chest-X-ray dictations as a free-text training target:

- per-finding phrase banks with 3–6 alternatives, slot-filled with severity adjectives and adverbs;
- combination phrasings for related findings (bilateral effusions, multiple nodules);
- mixed structural styles — sectioned with anatomical sub-headers, sectioned in prose, or pure prose without explicit headers;
- numbered IMPRESSION when more than one syndrome line is generated.

## CLI

```bash
python -m data.generate \
    --n 10000 \
    --seed 42 \
    --workers 32 \
    --out datasets/n10000 \
    --train-ratio 0.80 --val-ratio 0.10 --split-seed 0
```

Writes `<out>/{images, masks, labels.csv, annotations.json, reports.json, finding_definitions.json, splits/{train,val,test}.txt}`.

The split is stratified by `scenario` (the high-level case label that sampled the `FindingState`) so each regime contains the same syndrome distribution.

### Sharded multi-pod generation

For dataset sizes where a single pod's CPU is the bottleneck, pass `--start-idx` / `--total-n` / `--shard-only` so each pod produces a contiguous slice of indices into a shared output directory; assemble afterwards with `data.merge_shards`.

```bash
# pod k of K  (parallel; all pods write to the same /workspace/pixel-vs-prior/datasets/n1000000/)
python -m data.generate \
    --n 142857 --start-idx <start> --total-n 1000000 \
    --seed 42 --workers 16 --shard-only \
    --out /workspace/pixel-vs-prior/datasets/n1000000

# once all shards finished
python -m data.merge_shards --out /workspace/pixel-vs-prior/datasets/n1000000
```

The end-to-end orchestration lives in [`scripts/launch_1m_gen.sh`](../scripts/launch_1m_gen.sh).

### Recovering labels without re-rendering

[`recover_labels.py`](recover_labels.py) re-derives `labels.csv` and the splits from existing PNGs by replaying `sample_scenario` + `derive_labels` on the same per-image seeds — useful if a sharded run was interrupted before the records JSONLs were written, or if the dataset was generated by a third party and only images survive. Skips the expensive renderer, so a few hundred thousand images recover in a few minutes:

```bash
python -m data.recover_labels --out datasets/n600000 --workers 32
```

## Determinism and the scaling-prefix property

The CLI uses `seed + i` as the per-sample seed (where `i` is the 1-based image index), so the first `N` samples produced at `--seed 42` are bit-for-bit identical regardless of `--n`. Hence `datasets/n10000/` is a strict prefix of `datasets/n100000/`, and the scaling comparison in [`experiments/`](../experiments/) is *nested* rather than *paired*.

The val/test split has its own seed (`--split-seed 0`) that is independent of generation, so swapping `--seed` while keeping `--split-seed` unchanged keeps val/test indices stable.
